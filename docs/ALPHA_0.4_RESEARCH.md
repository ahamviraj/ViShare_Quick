# Alpha 0.4 protocol investigation

## Sources consulted

- Google's maintained Nearby Connections [`offline_wire_formats.proto`](https://github.com/google/nearby/blob/main/connections/implementation/proto/offline_wire_formats.proto): the outer `OfflineFrame` v1 structure and frame-type enumeration. The file declares Apache License 2.0. No schema source was copied into this repository.
- Google's [`offline_frames.cc`](https://github.com/google/nearby/blob/main/connections/implementation/offline_frames.cc): confirms that Nearby's implementation parses OfflineFrame protobufs and checks their validity.
- Google's [`offline_frames.cc` connection-response encoder](https://github.com/google/nearby/blob/main/connections/implementation/offline_frames.cc): serializes both legacy `status` and the newer `response` enum for compatibility, includes OS information, sets multiplex support to zero for this helper path, and sets the safe-to-disconnect version from a runtime flag.
- Grishka/NearDrop [`PROTOCOL.md`](https://github.com/grishka/NearDrop/blob/master/PROTOCOL.md): a reverse-engineered description of the LAN Quick/Nearby Share flow. It states that each TCP protobuf message uses a four-byte big-endian length prefix, describes the initial connection request and UKEY2 exchange, and explicitly says its scope is observed Wi-Fi LAN behavior. It is documentation, not an authoritative Google wire specification. No code was copied.
- Google's [Nearby Connections overview](https://developers.google.com/nearby/connections/overview): confirms the product-level API supports encrypted nearby data exchange and file payloads, but does not specify this Quick Share TCP wire flow.
- Google's open-source [UKEY2 implementation](https://android.googlesource.com/platform/external/ukey2/): the Android 14 branch documentation and implementation history were consulted; this project implements only the opt-in P256_SHA512 responder path and does not vendor Google code.
- Dhiva-Labs [NearShare](https://github.com/Dhiva-Labs/NearShare): maintained implementation notes corroborate the order of the two plaintext connection responses and the switch to SecureMessage afterward. Its repository advertises an MIT license. These notes are corroboration, not a Google Quick Share specification; no code was copied.
- Google's UKEY2 [`ukey.proto`](https://android.googlesource.com/platform/external/ukey2/+/661b17d2d2189eb6d6059734c9635bf933a52c75/src/main/proto/ukey.proto) and [Android 14 protocol documentation](https://android.googlesource.com/platform/external/ukey2/+/refs/heads/android14-d2-release): documents `Ukey2Message` fields, enum values, ClientInit fields, and version/random validation. The current `main` branch no longer exposes that historical schema path, so this immutable source revision is linked.

## Behaviors supported by sources

- Nearby Connections defines `OfflineFrame.version = V1` and a nested V1 frame with a numeric type. The inspector recognizes the documented outer fields, type enum, and matching body field without decoding peer-identifying contents.
- NearDrop documents the observed LAN connection as TCP with four-byte big-endian lengths framing protobuf messages. The inspector handles partial reads and imposes a 1 MiB maximum.
- A complete length-prefixed frame that is not an OfflineFrame v1 is now reported as an unrecognized message family, rather than as an invalid length or truncated TCP frame. The inspector does not claim the payload is UKEY2 without parsing/validating that message family.
- The pinned Google UKEY2 schema assigns `Ukey2ClientInit.version=1`, `random=2`, repeated `cipher_commitments=3`, and `next_protocol=4`. Nested `CipherCommitment` uses `handshake_cipher=1` and `commitment=2`. The inspector reports version support, random presence/length, commitment count, recognized cipher identifiers, commitment byte lengths, duplicated/missing/malformed fields, and whether `next_protocol` matches the documented Android reference value. It never prints random or commitment bytes or the protocol string.
- Cipher enum IDs 100 (`P256_SHA512`) and 200 (`CURVE25519_SHA512`) are recognized by the schema; that recognition does not claim local cryptographic support. For these SHA-512 suites the diagnostic flags commitment lengths other than 64 bytes. Per the Android 14 reference implementation, `AES_256_CBC-HMAC_SHA256` is a supported next-protocol value for that implementation. A match in an incoming message is reported only as a match to this documented value, not as proof that a later Quick Share protocol is implemented.
- Two Android 14 XPad diagnostic runs reported a recognized OfflineFrame `CONNECTION_REQUEST`, followed by a recognized UKEY2 `CLIENT_INIT`: version 1; 32-byte random; one cipher commitment with ID 100 (`P256_SHA512`) and 64 commitment bytes; and a 23-byte `next_protocol` matching the documented Android 14 reference value. The logs reported no parser issues. These are user-provided sanitized device observations, not checked-in packet bytes or cryptographic verification of the commitment. In the earlier read-only build, no further frame arrived before timeout because the program did not respond.
- In later user-reported opt-in runs, Android sent `CLIENT_FINISH`; the program reported commitment verification and P-256 ECDH/HKDF derivation, but the Android UI remained at “Connecting…” and eventually failed. Those runs predate this plaintext response implementation. They do not establish that `CONNECTION_RESPONSE` was sent or that the peer accepted it.
- Google's Android 14 UKEY2 protocol documentation specifies `CLIENT_INIT` → `SERVER_INIT` → `CLIENT_FINISHED`. The server must check version/random, the offered cipher commitments and supported next-protocol string before selecting a cipher. The documented cipher identifiers include `P256_SHA512` (100) and `CURVE25519_SHA512` (200). The reference C++ implementation history shown in the Android 14 source uses P-256 and `AES_256_CBC-HMAC_SHA256` as its next protocol; that does not establish which suite/value this XPad offers or that newer Quick Share uses only that value.
- `SERVER_INIT` requires a fresh 32-byte random, selected cipher, version 1, and a schema-encoded `GenericPublicKey`. In the P-256 encoding, the point coordinates are big-endian signed byte strings as specified by SecureMessage's key schema; using a generic SEC1 public-key byte string would be a different encoding.
- For `CLIENT_FINISHED`, Google requires the server to verify the commitment for the selected cipher against the serialized outer UKEY2 ClientFinish protobuf, then parse and validate the peer public key. The transport prefix is stripped before the reference API hashes/stores messages. The Android 14 implementation performs P-256 ECDH, SHA-256 hashes the ECDH result, and uses HKDF-SHA256 with salts `UKEY2 v1 auth` and `UKEY2 v1 next` and info equal to serialized ClientInit/ServerInit UKEY2 protobufs concatenated. The authentication output is intended for out-of-band comparison. The client expects no response after ClientFinished; errors terminate the connection.
- NearDrop's reverse-engineered notes describe the same broad sequence and a later connection response/encrypted flow. They are useful corroboration for observed Quick Share LAN behavior, not normative requirements for all Android versions.
- Google's OfflineFrame schema assigns `CONNECTION_RESPONSE` type 2 and `ConnectionResponseFrame` body field 3. Its nested legacy `status` is field 1 and is documented as `STATUS_OK` or `STATUS_CONNECTION_REJECTED`; `handshake_data` is field 2; the newer `response` enum is field 3 (`UNKNOWN_RESPONSE_STATUS=0`, `ACCEPT=1`, `REJECT=2`); `os_info` is field 4; and `multiplex_socket_bitmask` is field 5. Google's current Nearby response encoder writes both legacy success status and `ACCEPT` for backward compatibility, along with OS information and a zero multiplex bitmask. This implementation follows that schema shape, selects the local OS enum, and omits optional fields for which it has no configured value.
- The opt-in connection stage occurs only after ClientFinish commitment verification and key derivation. It sends one framed OfflineFrame v1 `CONNECTION_RESPONSE` with legacy status 0 (`STATUS_OK`), enum `ACCEPT=1`, OS info, and multiplex bitmask 0; it then reads exactly one bounded, length-prefixed peer response and accepts either `response=ACCEPT` or legacy `status=0`. Unknown enum values, malformed/duplicate fields, conflicting statuses, explicit rejection, wrong frame types, timeout, and disconnect terminate the connection. Unknown nonzero legacy statuses are rejected as unsupported; their numeric meaning is not guessed. A one-shot state object prevents duplicate send/receive transitions. A TCP response does not establish that Android accepted the connection at the UI level.
- Both NearDrop and NearShare describe each side sending a plaintext connection response after UKEY2, followed by encrypted SecureMessage traffic. That transition is reverse-engineered behavior; the published Google schema establishes the response structure and enum values but is not a normative Quick Share sequencing specification. Google’s current encoder also includes optional `safe_to_disconnect_version`; this program omits it and closes after validating the peer response. That may affect compatibility and must be tested on the XPad.
- Windows uses the documented `OsInfo.WINDOWS=3`. The schema labels `OsInfo.LINUX=100` as a G3 test environment value; the Linux response selection is therefore not established as Quick Share-compatible. The current controlled Android test target is the Windows host. The `CONNECTION_RESPONSE` sender/receiver exchange has not yet been tested against Android.
- No encrypted SecureMessage was sent or read in this stage. The next layer requires exact `securemessage.proto`/`securegcm.proto` envelope encoding, HMAC-SHA256 validation over the correct serialized header/body bytes, AES-256-CBC with correct padding/IV handling, directional HKDF key derivation from `next_secret`, and independent sequence counters. NearDrop and NearShare describe these mechanisms, but this project has not implemented or validated them. The receiver must also implement paired-key fallback and the sharing introduction/consent state before any payload transfer. File transfer remains out of scope.
- Frame inspection remains read-only by default. The separate `--ukey2-handshake` mode is opt-in and sends a UKEY2 response only after validating a supported ClientInit; it then sends the plaintext connection response only after ClientFinish commitment validation. It does not decrypt secure messages or continue into Quick Share transfer. Normal logs contain frame size, family, enum type, and safe field-validation status. Hex output is opt-in, limited to 96 bytes from one selected frame, and includes the length prefix.

## Verified UKEY2 server flow and limitations

- Two real Android 14 XPad runs report a 136-byte ClientInit payload (140 bytes with the four-byte TCP prefix): version 1, 32-byte random, one cipher ID 100 (`P256_SHA512`) commitment of 64 bytes, a 23-byte `next_protocol` matching the Android 14 reference value, and no parser issues. These are sanitized user-provided observations. The raw frame is not retained; length alone does not prove the commitment is valid.
- The server accepts only version 1, random length 32, the documented next-protocol value, and an offer containing a structurally well-formed 64-byte P256_SHA512 commitment. The offer alone does not prove that commitment is correct; it is verified against the serialized ClientFinish only after that message arrives. The server then selects P256_SHA512, generates a fresh P-256 key and 32-byte random, and sends outer `Ukey2Message(type=SERVER_INIT, message_data=Ukey2ServerInit(...))`.
- `Ukey2ServerInit` contains version=1, the fresh random, cipher=100, and a serialized `GenericPublicKey`. SecureMessage encodes `GenericPublicKey.type=EC_P256(1)` and `ec_p256_public_key` field 2, with x/y as required big-endian two's-complement coordinates. The encoder uses minimal positive signed encoding: a leading zero is included when the coordinate high bit is set. The 4-byte big-endian length prefix wraps this protobuf on TCP.
- The ClientInit cipher commitment is SHA-512 over the serialized outer UKEY2 `CLIENT_FINISH` protobuf, whose `message_data` contains `Ukey2ClientFinished.public_key` as a serialized `GenericPublicKey`. The committed bytes include the UKEY2 outer protobuf envelope and exclude the separate 4-byte TCP length prefix. Google’s UKEY2 transport shell reads/strips that prefix before calling its handshake API; its implementation hashes the resulting serialized `Ukey2Message` bytes. The verifier uses constant-time comparison before parsing the ClientFinish public key.
- The server parses exactly the P-256 GenericPublicKey schema, validates the coordinate encoding and on-curve point, then computes P-256 ECDH. The Android 14 implementation's `KeyAgreementSha256` hashes the raw ECDH output with SHA-256. Its `CryptoOps::Hkdf` is HKDF-SHA256 (the P256_SHA512 suffix identifies the commitment hash here, SHA-512). The verification output uses salt `UKEY2 v1 auth`; the next-protocol output uses salt `UKEY2 v1 next`; both use info `serialized_ClientInit_Ukey2Message || serialized_ServerInit_Ukey2Message`. The implemented reference lengths are 32 bytes for each output (the reference API allows a caller-selected auth length from 1–32; the reference HKDF default and next-protocol master key are 32 bytes).
- This selects the concrete Android 14 reference implementation behavior where the general protocol overview's phrase “hash from HandshakeCipher” is underspecified for the key-agreement/KDF step. The source's `KeyAgreementSha256` and `CryptoOps::Hkdf` explicitly use SHA-256, while ClientFinish commitment verification uses SHA-512. This implementation follows that concrete reference code path. Unit tests exercise it with deterministic synthetic keys and protobuf fixtures, not Android packet captures or Google-published byte-for-byte interoperability vectors.
- On invalid ClientInit, the Android reference can send a typed UKEY2 Alert before terminating. This experimental responder instead rejects the offer and closes without sending an alert. On ClientFinish type, parse, commitment, or key failures, it closes without a follow-up response, consistent with the reference behavior that the client expects no response after ClientFinish. It logs only safe failure reasons and never logs cryptographic values.
- After ClientFinish validates, the responder derives the verification and next-secret outputs but does not perform out-of-band authentication. The opt-in flow then exchanges plaintext connection ACCEPT responses and closes. There is no encrypted SecureMessage handling, paired-key processing, payload negotiation, BLE trigger, or file transfer.
- `--inspect-frames` remains read-only and is the default. `--ukey2-handshake` is a separate explicit opt-in that sends `SERVER_INIT` and `CONNECTION_RESPONSE ACCEPT`, then validates the peer's plaintext response. Synthetic deterministic unit tests cover the state machine and invalid paths, but no independent Google-produced byte-for-byte vector or Android response-exchange run has verified interoperability. Real-device validation remains outstanding.
- No maintained, dedicated Python UKEY2 library was established. The implementation uses `cryptography` for P-256, ECDH, SHA-256/SHA-512, secure randomness supplied by Python's `secrets`, and HKDF-SHA256; protobuf serialization is independently encoded from the cited schema fields. No Google or NearDrop code is copied. The installed environment has `cryptography`; project packaging now declares it as a runtime dependency.
- The opt-in bounded hex flags can still reveal at most 96 bytes of a selected frame (including the TCP prefix); they remain disabled by default. Normal diagnostics omit field contents. The 1 MiB cap is a defensive local bound, not a protocol maximum.

## Paired-key sequence-3 diagnostic finding (2026-11-09)

- A later user-reported run of `--ukey2-handshake --paired-key-response` stopped with `Expected authenticated sequence-3 PAIRED_KEY_RESULT.` That specific message is raised only after the inbound frame has passed HMAC verification, AES-CBC/PKCS#7 decryption, sequence validation, OfflineFrame parsing, and payload parsing. The verified finding is therefore narrower and stronger than the earlier "no response" interpretation: Android did send an authenticated, decryptable inbound sequence-3 frame; its sharing type was not a complete `PAIRED_KEY_RESULT`.
- The failed message does not identify Android's sequence-3 frame type and does not prove that Android rejected the empty `PairedKeyEncryptionFrame`. A `KEEP_ALIVE`, a `DISCONNECTION`, a multi-chunk BYTES result, or another transport frame would all produce the same state-machine error.
- The reviewed receivers tolerate interleaved transport traffic during this stage: NearShare `_recv_encrypted()` acknowledges/skips `KEEP_ALIVE`, squick-share `InboundSession.handle` acknowledges `KEEP_ALIVE`, and both accumulate BYTES chunks until `LAST_CHUNK`. The current ViShare Quick response state machine instead assumes the immediately next authenticated frame is a complete single-frame result. That assumption is the leading local suspect, not a proven protocol defect.
- An opt-in `--protocol-timeline` mode now reports the actual inbound sequence-3 frame metadata (offline type, sharing type, payload ID, total size, offset, chunk length, LAST_CHUNK state, completeness, authentication/decryption state) without logging payload bytes or identity material. The next real-device run must identify the frame before any state-machine change is made.


## Confirmed `BANDWIDTH_UPGRADE_RETRY` finding and fix (2026-11-10)

- The follow-up real-device run resolved the sequence-3 question. The inbound frame was authenticated, decrypted, and reported as `offline=BANDWIDTH_UPGRADE_RETRY` with no sharing type and no payload. It was a legal transport-control frame, not an Android paired-key rejection and not a `KEEP_ALIVE`.
- Google `offline_wire_formats.proto` confirms `V1Frame.FrameType.BANDWIDTH_UPGRADE_RETRY = 12` and its body field 13 (`bandwidth_upgrade_retry`). `BandwidthUpgradeRetryFrame` has `repeated Medium supported_medium = 1` and `optional bool is_request = 2`. The schema documents that `is_request = true` expects the remote endpoint to send back its latest supported-medium list. The observed frame did not report `is_request=true`.
- The reviewed receivers agree on the local behavior for this stage: NearShare `_recv_sharing_frame()` ignores non-`PAYLOAD_TRANSFER` frames, NearDrop ignores unhandled offline frames, and squick-share logs `default: ignoring ...`; all acknowledge `KEEP_ALIVE`. None treats a bandwidth-control frame as fatal to the paired-key stage.
- ViShare Quick previously assigned fixed sequence numbers to application messages and passed the next authenticated frame directly to `accept_peer_result()`. That was the proven defect. The response stage now uses one transport-wide monotonic inbound counter, skips authenticated transport-control frames, acknowledges `KEEP_ALIVE` with `ack=true`, reports `DISCONNECTION` as a peer disconnect, and caps skipped control frames at 16 per wait. It does not reply to `BANDWIDTH_UPGRADE_RETRY` in this iteration.
- The four outbound paired-key frames (empty PKE DATA + terminator, `PAIRED_KEY_RESULT.UNABLE` DATA + terminator) are unchanged. No identity material, signature, certificate, secret hash, or QR data is fabricated, and no cryptography is weakened.
- The sanitized `--protocol-timeline` output for a skipped retry reports `IN SKIP offline=BANDWIDTH_UPGRADE_RETRY`, `retry_is_request`, and medium names without body bytes. Synthetic tests cover the retry skip, keep-alive ack, global sequence accounting, flood cap, disconnection handling, and timeline redaction.
- Android acceptance of the empty PKE and the reciprocal `PAIRED_KEY_RESULT`/Introduction remain unverified. The next real-device run must confirm those messages. If Android repeats `BANDWIDTH_UPGRADE_RETRY` with `is_request=true` or stalls, the next iteration should implement the schema-documented retry reply with `is_request=false` and no supported media.

## Approved no-credential PKE placeholder change (2026-11-10)

- The state-machine investigation concluded that message ordering, transport-control skipping, and the 15 s stage timeout all match the reviewed references. The remaining protocol-level deviation was the empty `PairedKeyEncryptionFrame`: no reviewed implementation emits one, including Google's own no-certificate fallback.
- Google `paired_key_verification_runner.cc` always sets both fields: `signed_data` is a signature, or `GenerateRandomBytes(kNearbyShareNumBytesRandomSignature)` with `kNearbyShareNumBytesRandomSignature = 72` when no signature is available; `secret_id_hash` is a certificate hash, or random bytes when no certificate is available (6-byte authentication-token hash). NearDrop, NearShare, and squick-share use the same 72/6 random-shape fallback and report `UNABLE`.
- With explicit approval, `build_paired_key_encryption_frame()` now emits fresh `secrets.token_bytes(72)` in `signed_data` and fresh `secrets.token_bytes(6)` in `secret_id_hash`, and keeps `PairedKeyResultFrame.UNABLE`. `optional_signed_data`, `qr_code_handshake_data`, and `supports_provisioning` remain absent.
- The placeholders assert no identity and are not a certificate, signature, or certificate-derived hash. They are generated per call, never hardcoded or copied. The change does not alter the state machine, transport-wide sequence counters, 15 s deadline, transport-control skip, or the opt-in `--paired-key-response` gate.
- Tests now assert the 72/6 field lengths, the absence of the identity-bearing optional fields, and that two calls differ; no test asserts a specific random value. README and the CLI warning text were updated from "empty PKE" to the no-credential placeholder wording.
- Android acceptance of the placeholder PKE, the reciprocal `PAIRED_KEY_RESULT`, and the subsequent Introduction remain unverified. The next real-device run must confirm whether Android now progresses past the paired-key stage, and should capture the Android UI state at the same time.
