This is a source comparison for the protocol stage after the two plaintext Nearby `CONNECTION_RESPONSE ACCEPT` messages. The latest user-reported Android 14 XPad runtime output says one 214-byte SecureMessage authenticated and decrypted as Nearby `PAYLOAD_TRANSFER` → sharing `PAIRED_KEY_ENCRYPTION`, sequence 1. The observed outer lengths were 177-byte `header_and_body` and a 32-byte signature. The raw bytes are not present in this repository, so this report cannot independently reproduce that authentication result. Android still showed Connecting → Failed; no successful Quick Share connection or transfer has been demonstrated.

The principal result is that the client-to-server receive schedule and SecureMessage processing rules match across NearShare and NearDrop, with squick-share corroborating envelope handling. The XPad observation confirms that this device sends the first paired-key offer after ACCEPT. The implementations still disagree about whether the receiver sends its own offer before or after the peer's offer. Chromium's `PairedKeyVerificationRunner::Run()` always sends a PKE frame first, then a `PAIRED_KEY_RESULT`, and then waits for the peer's reciprocal PKE and result; when it has no private certificate it fills `signed_data` and `secret_id_hash` with random bytes and normally reports `UNABLE`. This project has no Google-account-provisioned certificate or secret material, so the opt-in response mode sends the reference-shaped no-credential placeholder: 72 fresh random bytes in `signed_data` and 6 fresh random bytes in `secret_id_hash`, plus `UNABLE`. These are random protocol placeholders, not a signature, certificate, identity, or actual secret-ID hash. Whether Android accepts the placeholder remains unverified.

## Current read-only encrypted-frame diagnostic

The receiver derives Android-client-to-laptop-server keys from the UKEY2 `next_secret`. This calculation is cross-checked against NearShare `crypto.py::_derive_session_keys` / `D2DCipher` and NearDrop `NearbyConnection` key-derivation and receive helpers. squick-share `KeyDerivation` and `SecureChannel.open` corroborate SecureMessage processing. This is source-level agreement, not an external known-answer vector and does not independently prove UKEY2 interoperability with Android. The inspector reuses the four-byte big-endian frame reader, 1 MiB cap, and 10-second overall deadline, then consumes at most one frame.

The parser checks required outer `SecureMessage` fields and rejects missing, duplicate, wrong-wire-type, truncated, or inconsistent fields. It retains exact TCP wire bytes, serialized `header_and_body`, and signature in memory only; they are excluded from representations and never printed or written to disk. It verifies HMAC-SHA256 in constant time over the exact received `header_and_body` bytes before parsing them. It then requires HMAC-SHA256/AES-256-CBC, `DEVICE_TO_DEVICE_MESSAGE` metadata type 13/version 1, decrypts and checks PKCS#7 padding, parses `DeviceToDeviceMessage`, enforces sequence number 1 for the first inbound frame, and structurally decodes the authenticated OfflineFrame and complete BYTES sharing Frame where supported. Any failure stops processing; no alternate key direction is tried. Plaintext, IV, signature, key material, and sharing message contents are never logged.

The outer schema assignments are confirmed in Google's archived Apache-2.0 [`securemessage.proto`](https://github.com/google/securemessage/blob/master/proto/securemessage.proto): `SecureMessage.header_and_body=1`, `signature=2`; `HeaderAndBody.header=1`, `body=2`; `Header.signature_scheme=1`, `encryption_scheme=2`, `iv=5`, `public_metadata=6`. NearDrop's collected Apache-2.0 [`device_to_device_messages.proto`](https://github.com/grishka/NearDrop/blob/master/NearbyShare/ProtobufSource/device_to_device_messages.proto) defines D2D `message=1`, `sequence_number=2`; `securegcm.proto` defines `GcmMetadata.type=1`, `version=2`, `DEVICE_TO_DEVICE_MESSAGE=13`. These structures are decoded only after successful HMAC verification.

The `--inspect-encrypted-frame` option requires `--ukey2-handshake`, because the program must first perform the existing experimental UKEY2 and plaintext ACCEPT exchange. Consequently this mode sends `SERVER_INIT` and plaintext `CONNECTION_RESPONSE ACCEPT` as before, but never sends an encrypted message. The separate `--paired-key-probe` option authenticates and structurally checks a first paired-key offer, then reads at most one subsequent authenticated frame; it sends no paired-key response, consent decision, or file data. The separate `--paired-key-response` option performs the same UKEY2/ACCEPT exchange, waits for the authenticated Android PKE offer (receive sequence 1) and its zero-length `LAST_CHUNK` terminator (receive sequence 2), then sends a no-credential `PairedKeyEncryptionFrame` (72 fresh random `signed_data` bytes, 6 fresh random `secret_id_hash` bytes, other optional fields absent) and `PairedKeyResultFrame.UNABLE` as outbound sequences 1–4 under independent server-to-client keys. It then authenticates the peer result (receive sequences 3–4) and an optional Introduction (receive sequence 5). It asserts no identity, requests no consent, and transfers no files. The three encrypted-stage modes are mutually exclusive. The default inspector remains read-only. Existing hex dumps remain separate and opt-in; encrypted inspection does not dump frame bytes.

## Source-backed sequence and unresolved branch

The established common outer transport in the inspected implementations is TCP with a four-byte big-endian length prefix for each serialized protobuf frame. The first two `CONNECTION_RESPONSE ACCEPT` messages are plaintext Nearby OfflineFrames. The independent implementations then wrap serialized OfflineFrames in SecureMessage-protected device-to-device messages. They carry sharing-layer protobuf `Frame` messages in Nearby `PAYLOAD_TRANSFER` frames with a BYTES payload. File bytes use FILE payloads after the sharing-layer introduction/consent stage.

The paired-key sequence differs across the implementations:

* NearDrop `InboundNearbyConnection.processConnectionResponseFrame` sends a local PKE offer after accepting the plaintext response. Its `processPairedKeyEncryptionFrame` then accepts the peer offer and sends `PAIRED_KEY_RESULT.UNABLE`; `processPairedKeyResultFrame` moves to the introduction state.
* squick-share `InboundSession.run` also calls `SharingFrames.pairedKeyEncryption()` before entering `awaitingPairedKeyEncryption`. Its handler accepts PKE only in that state, calls `SharingFrames.pairedKeyResult()`, then waits for the peer result before Introduction. `OutboundSession.run` additionally obtains optional QR handshake data from `qrSession?.handshakeSignature(authString:)` and passes it into its PKE builder. The builder's complete inbound identity-material semantics are not established here.
* NearShare `InboundConnection._handshake` waits for the phone's PKE offer first, replies with a PKE message, receives the peer result, and sends `UNABLE` before entering its sharing phase. The source comment explicitly describes its own `signed_data` and `secret_id_hash` as random fallback values.
* The latest XPad runtime report shows Android sent its PKE offer first. This establishes the device's observed first-message order for the tested run, but does not establish what response makes the peer continue.

Because the laptop has no reviewed contact certificate/identity material and the implementations' fallback values are random placeholders, no identity-valid PKE response can be synthesized. The opt-in probe therefore validates the incoming message structure, reports only field presence/lengths, then waits for at most one additional inbound frame without sending. The separate `--paired-key-response` mode is also honest about this limit: after the offer and terminator authenticate, it sends the reference-shaped no-credential placeholder, a `PairedKeyEncryptionFrame` with 72 fresh random `signed_data` bytes and 6 fresh random `secret_id_hash` bytes, followed by `UNABLE`. Those bytes are random protocol placeholders, not a signature, certificate, identity, or actual secret-ID hash. Chromium's own no-certificate fallback uses the same 72/6 random shape.

## Encrypted envelope and directional state

### Serialized message layers

The independent implementations agree on this logical nesting for post-UKEY2 traffic:

```text
4-byte big-endian TCP length
  SecureMessage
    header_and_body = serialized HeaderAndBody
      Header (HMAC_SHA256 signature scheme, AES_256_CBC encryption scheme, IV, public metadata)
      body = encrypted serialized securegcm.DeviceToDeviceMessage
        message = serialized Nearby OfflineFrame
          PAYLOAD_TRANSFER carrying BYTES sharing Frame or FILE payload chunk
    signature = HMAC-SHA256 over the serialized header_and_body bytes
```

This is the format used by NearShare `D2DCipher.encrypt/decrypt`, squick-share `SecureChannel.seal/open`, and NearDrop `NearbyConnection`'s secure-frame send/receive helpers. The outer SecureMessage schema defines `header_and_body` and `signature`; its Header defines signature/encryption schemes, IV, and public metadata. `securegcm.DeviceToDeviceMessage` in NearDrop's schema collection defines `message=1` and `sequence_number=2`; `securegcm.GcmMetadata` defines the message type/version metadata. The implementations identify the metadata type as `DEVICE_TO_DEVICE_MESSAGE` (enum value 13) and version 1.

For this reverse-engineered path, encryption is AES-256-CBC with PKCS#7 padding and a fresh IV. Authentication is HMAC-SHA256 over the exact serialized `header_and_body` bytes. Implementations authenticate before CBC decryption/parsing, compare MACs in constant time, then validate metadata, padding, inner protobuf, and sequence. CBC alone is not authenticated encryption; the MAC-before-decrypt rule is essential. The current code preserves the exact received byte string used for the MAC instead of parsing and reserializing it first.

### Keys and sequence numbers

UKEY2 first derives `next_secret` using HKDF-SHA256 with salt `UKEY2 v1 next` and info equal to serialized ClientInit || serialized ServerInit. The current `ukey2.py` retains the serialized Ukey2Message payloads (excluding the four-byte transport prefixes), matching NearShare `crypto.py::_derive_session_keys` and NearDrop `NearbyConnection` transcript handling. For the received client-to-server D2D direction, the schedule uses HKDF-SHA256(next_secret, salt=SHA256(`D2D`), info=`client`) to derive a 32-byte D2D key, then HKDF-SHA256(D2D key, salt=SHA256(`SecureMessage`), info=`ENC:2`) and `SIG:1`, each 32 bytes. NearShare and NearDrop independently select these client keys when receiving as server; squick-share's `KeyDerivation` agrees with the labels and role split.

The code uses separate send and receive counters carried in `DeviceToDeviceMessage.sequence_number`; NearShare and squick-share increment from zero before first use, and NearDrop tracks separate client/server counters. Therefore the first expected inbound client sequence is 1. The read-only inspector enforces that first value. The paired-key probe accepts sequence 1 and optionally one sequence-2 follow-up. The response mode additionally enforces inbound sequences 1–4 (plus optional 5) and uses an independent outbound counter for sequences 1–4. It never reuses the receive direction's keys or counter.

The inspected sources provide a mutually corroborating implementation recipe, not a Google-issued Quick Share interoperability test vector. In particular, no deterministic external key/packet known-answer vector was available to verify this repository's outputs byte-for-byte. The inspector does not silently reserialize transcript material or reuse server-direction keys for receive.

## Pairing exchange and introduction schema

### `PairedKeyEncryptionFrame` structure and security boundary

NearDrop's collected [`wire_format.proto`](https://github.com/grishka/NearDrop/blob/master/NearbyShare/ProtobufSource/wire_format.proto) defines `PairedKeyEncryptionFrame` as four **optional bytes** fields: `signed_data=1`, `secret_id_hash=2`, `optional_signed_data=3`, and `qr_code_handshake_data=4`. Therefore protobuf itself marks none of those fields required. The sharing envelope is `Frame.version=1`, `Frame.v1=2`; `V1Frame.type=1` uses `PAIRED_KEY_ENCRYPTION=3`, and the matching `V1Frame.paired_key_encryption` body is field 4. The body must be present for this message type, but a protobuf parser cannot infer semantic validity or cryptographic verification from field presence or lengths.

The schema comments describe `signed_data` as signed/encrypted data and `secret_id_hash` as a certificate-ID hash. For `qr_code_handshake_data`, the comments distinguish an incoming-connection signature of the UKEY2 token from an outgoing-connection HKDF over connection/UKEY2 token material. These comments do not provide a complete byte-level algorithm, certificate lookup policy, signature input/canonicalization, key binding, or validation recipe. In particular, a `signed_data` field name does not prove that its content contains a valid signature.

Source behavior confirms why a responder must not copy placeholder bytes. NearShare `InboundConnection._handshake` sets `signed_data=os.urandom(72)` and `secret_id_hash=os.urandom(6)`, and its source comment labels these as random fallback values followed by `UNABLE`. NearDrop `InboundNearbyConnection.processConnectionResponseFrame` likewise fills 72 random bytes and 6 random bytes before sending its PKE offer; `processPairedKeyEncryptionFrame` replies with `PAIRED_KEY_RESULT.UNABLE`. NearDrop's [`PROTOCOL.md`](https://github.com/grishka/NearDrop/blob/master/PROTOCOL.md) calls these random values a practical fallback, not identity authentication. squick-share's `InboundSession.run` sends `SharingFrames.pairedKeyEncryption()` and its PKE handler reads `signedData`, `secretIDHash`, and optional QR data before sending a paired-key result. `OutboundSession.run` obtains optional `qrSession?.handshakeSignature(authString:)` and passes it to the PKE frame builder. That indicates a real QR-signature path exists, but the builder/signature/certificate semantics cannot be substituted without the local identity and verified QR pairing context.

Security checks for a future real pairing implementation must validate the exact PKE variant against the associated trusted certificate or QR handshake context, verify the signature/MAC and key binding using the protocol-defined bytes, validate `secret_id_hash` against a trusted certificate ID, reject malformed/duplicate fields, and only report paired identity after all checks pass. This probe performs none of those identity checks: it authenticates the outer SecureMessage, validates PKE protobuf structure, and reports safe metadata only. A valid channel HMAC proves possession of this session's UKEY2-derived traffic key, not the sender's real-world identity.

### No-certificate response decision

Chromium's `PairedKeyVerificationRunner::Run()` is the most complete published state machine for this stage. `Run()` always sends a PKE frame first, then a `PairedKeyResultFrame`, then waits for the peer's reciprocal PKE and result. When the runner has no private certificate, it still emits a PKE frame but fills `signed_data` with a random 72-byte value (`kNearbyShareNumBytesRandomSignature`) and `secret_id_hash` with a random 6-byte value (`kNearbyShareNumBytesAuthenticationTokenHash`), then normally reports `UNABLE`. NearDrop, NearShare, and squick-share use the same random-filler fallback pattern.

This project does not possess those certificate-backed fields, so it sends the reference-shaped no-credential placeholder: `signed_data` with 72 fresh random bytes and `secret_id_hash` with 6 fresh random bytes, followed by `PairedKeyResultFrame.UNABLE`. The placeholders are random protocol values, not a signature, certificate, identity, or actual secret-ID hash. The four outbound OfflineFrames are protected by separately derived server-to-client HKDF keys and sequences 1–4. The state machine requires the Android offer and zero-length terminator to authenticate before any outbound byte is written, then authenticates the peer result and optional Introduction. It reports the observed peer status (for example `SUCCESS`, `FAIL`, or `UNABLE`) without treating it as local identity proof.

This no-credential placeholder variant is an honest fallback, not a demonstrated interoperable pairing. Android may reject, ignore, or close on it; only a real device test can decide. A meaningful `SUCCESS` path requires Google-account-provisioned certificate material (`secret_id`, authenticity key, public key, X.509 certificate, and encrypted metadata) that this repository does not have and must not fabricate.

NearDrop's collected `wire_format.proto` defines a versioned sharing `Frame`. In `V1Frame.FrameType`, `INTRODUCTION=1`, `RESPONSE=2`, `PAIRED_KEY_ENCRYPTION=3`, and `PAIRED_KEY_RESULT=4`; their corresponding `V1Frame` body fields are `introduction=2`, `connection_response=3`, `paired_key_encryption=4`, and `paired_key_result=5`. These are application sharing messages, not the outer Nearby OfflineFrame type enum.

`IntroductionFrame` includes repeated `file_metadata` (field 1), optional text metadata, package/Wi-Fi/app/stream metadata, `start_transfer`, and `use_case`. Its `FileMetadata` fields include `name=1`, `type=2`, `payload_id=3`, `size=4`, `mime_type=5`, `id=6`, `parent_folder=7`, `attachment_hash=8`, and `is_sensitive_content=9`. `payload_id` associates the offer with a later Nearby FILE payload; metadata does not contain file bytes. The generated schema enum includes file categories such as image, video, Android app, audio, document, and contact card. A receiver must reject unsupported/ambiguous metadata and must not trust names or sizes as paths or allocation instructions.

After Introduction, the file receiver implementations request or apply user consent. Their sharing-layer response is `Frame` type `RESPONSE`, containing `ConnectionResponseFrame.status` (UNKNOWN=0, ACCEPT=1, REJECT=2, NOT_ENOUGH_SPACE=3, UNSUPPORTED_ATTACHMENT_TYPE=4, TIMED_OUT=5 in the collected schema). This response is not the plaintext Nearby connection response sent during transport setup. NearDrop's `processIntroductionFrame` delegates to its user-consent flow; squick-share validates content and emits a decision event; NearShare raises a transfer request and sends a response based on user choice.

The inspected flow carries file data in chunked Nearby FILE payloads keyed by the offered payload ID, with declared total size and chunk offsets. The common Nearby schema declares `PayloadTransferFrame` DATA/CONTROL/PAYLOAD_ACK message types and payload BYTES/FILE/STREAM types; `PayloadChunk` includes offset, body, index, and LAST_CHUNK. Some implementations send a final empty chunk to mark completion. That observed encoding should be confirmed against actual Android traffic before assuming all Android versions use an identical final marker. The cited Introduction and chunk fields establish transport framing/declared-size checks, but do not establish a universal end-to-end file digest. The `attachment_hash` field's exact use and validation policy also require source-level review before relying on it as a file-integrity check.

The paired-key exchange is also not synonymous with user consent. The sources show an `UNABLE` fallback and subsequent Introduction/consent path, but the exact Android behavior for known contacts, PIN comparison, certificate validation, and skipped prompts is not settled by these public schemas. Never treat `UNABLE` or an unauthenticated peer's Introduction as proof of identity.

## Common Nearby behavior vs Quick Share-specific findings

**Common Nearby schema/transport:** `OfflineFrame`, `PAYLOAD_TRANSFER`, payload type and ID, chunk offset/body/index/last-chunk, acknowledgements and keepalive-related transport messages. These structures are published by Google Nearby Connections. They do not, by themselves, define how Quick Share chooses sharing `Frame` order, consent UI, paired-key policy, or Android compatibility.

**Quick Share/reverse-engineered layer:** `sharing.nearby.Frame`, `IntroductionFrame`, `PairedKeyEncryptionFrame`, `PairedKeyResultFrame`, transfer-consent `ConnectionResponseFrame`, SecureMessage metadata use for this TCP flow, and the observed pairing state machine. The cited schemas were collected from Chromium-derived source and NearDrop describes decompiled GMS analysis. NearShare and squick-share are independent implementations of this behavior, not normative specifications.

## Uncertainties and compatibility caveats

1. The user-reported XPad result says its 214-byte frame authenticated with sequence 1 as `PAYLOAD_TRANSFER` → `PAIRED_KEY_ENCRYPTION`. Raw bytes were not supplied, so this run cannot independently confirm that result or inspect the actual PKE fields.
2. The XPad's first-message order is Android PKE first, but NearDrop/squick-share send their own PKE first. The implemented response mode replies only after the Android offer and terminator authenticate, but Android's acceptance of the random no-credential placeholder PKE is unverified.
3. The exact semantics and cryptographic validation of PKE fields, identity certificates, and secret-ID hashes are not sufficiently established for this project to generate a valid identity proof. Random filler in samples is explicitly not evidence of authentication.
4. The deterministic tests use locally generated synthetic schema-derived fixtures. They test parser/state behavior, not Android interoperability or any published byte-for-byte encrypted vector.
5. Public schemas and open implementations may target different Google Play services, Chromium, Android, or Quick Share releases. Android 14 evidence does not establish behavior on newer Android releases or other OEM builds.
6. OfflineFrame transport details are public Nearby behavior, but the sharing application protocol is not a complete public Quick Share specification. Optional Introduction fields, consent policy, progress and cancellation, and payload termination may vary.
7. A completed encrypted exchange would still not establish Android UI success or file transfer. That requires peer-validated state transitions and an end-to-end device transfer with integrity checks.

## Proposed implementation milestones

1. **Read-only authenticated frame inspection (implemented).** The opt-in mode reads one bounded frame, verifies HMAC before decryption, validates metadata/padding/sequence and supported inner envelopes, and reports safe types only. Tests are synthetic and no encrypted response is sent.
2. **Paired-key structural probe (implemented).** `--paired-key-probe` requires the first authenticated message to be sequence-1 PKE, reports only schema-field presence/lengths, and reads at most one authenticated sequence-2 follow-up. It sends no PKE response. Tests cover malformed structures, message order, authentication failure, timeout/disconnect, and prohibited state transitions.
3. **No-credential paired-key response (implemented, experimental).** `--paired-key-response` waits for the authenticated sequence-1 PKE offer and sequence-2 terminator, sends a no-credential `PairedKeyEncryptionFrame` (72 fresh random `signed_data` bytes, 6 fresh random `secret_id_hash` bytes, other optional fields absent) plus `PAIRED_KEY_RESULT.UNABLE` under independent server-to-client keys, then authenticates the peer result and optional Introduction. It sends no certificate, signature, identity proof, consent response, or file data. Synthetic tests cover builders, placeholder lengths, directional keys, ordering, terminators, and prohibited transitions; Android acceptance is unverified.
4. **Real paired-key identity.** Implement only after obtaining and validating Google-account-provisioned certificate material and an authoritative response construction, including signature input/canonicalization, certificate lookup, secret-ID hash validation, QR flows, and SUCCESS/FAIL/UNABLE semantics. Do not treat random placeholder PKE bytes as identity proof or as a SUCCESS path.
5. **Introduction and consent.** Parse/validate metadata into safe typed objects, enforce count/size/type limits and payload-ID association, expose an explicit consent decision, then send the schema-correct sharing response. Test all statuses and malformed/unsupported metadata without network/device requirements.
6. **Payload receiver.** Add bounded chunk reassembly, offset/overlap/duplicate and declared-size validation, payload ACK/state handling, cancellation/disconnection, safe destination naming, cleanup, and integrity reporting. Verify file hash semantics before claiming end-to-end integrity.
7. **Controlled Android validation.** Capture the Android 14 XPad's first encrypted frames, then verify the no-credential placeholder PKE response, pairing/Introduction/consent in staged tests. Only after a real file is received and independently checked may the project claim transfer support. Repeat across Android/GMS versions before broad compatibility claims.

* Google SecureMessage schema: [`SecureMessage`, `Header`, `HeaderAndBody`, `SigScheme`, `EncScheme`](https://github.com/google/securemessage/blob/master/proto/securemessage.proto). Repository status: [archived](https://github.com/google/securemessage).
* NearDrop sharing schema: [`Frame`, `V1Frame`, `IntroductionFrame`, `FileMetadata`, paired-key and response messages](https://github.com/grishka/NearDrop/blob/master/NearbyShare/ProtobufSource/wire_format.proto); D2D wrapper [`DeviceToDeviceMessage`](https://github.com/grishka/NearDrop/blob/master/NearbyShare/ProtobufSource/device_to_device_messages.proto); message type metadata [`GcmMetadata`](https://github.com/grishka/NearDrop/blob/master/NearbyShare/ProtobufSource/securegcm.proto).
* NearDrop crypto/state: [`NearbyConnection`](https://github.com/grishka/NearDrop/blob/master/NearbyShare/NearbyConnection.swift) secure send/receive, `encryptAndSendOfflineFrame`, D2D sequence tracking, HMAC/AES/HKDF; [`InboundNearbyConnection`](https://github.com/grishka/NearDrop/blob/master/NearbyShare/InboundNearbyConnection.swift) `processReceivedFrame`, `processConnectionResponseFrame`, `processPairedKeyEncryptionFrame`, `processPairedKeyResultFrame`, and `processIntroductionFrame`.
* NearShare: [`D2DCipher.encrypt/decrypt` and `_derive_session_keys`](https://github.com/Dhiva-Labs/NearShare/blob/main/nearshare/core/crypto.py); [`InboundConnection._handshake`, `_send_encrypted`, `_recv_encrypted`, `_send_sharing_frame`, `_sharing_phase`](https://github.com/Dhiva-Labs/NearShare/blob/main/nearshare/core/connection.py).
* squick-share: [`KeyDerivation`](https://github.com/Mukesh-devs/squick-share/blob/main/Packages/QuickShareCore/Sources/QuickShareCore/Crypto/KeyDerivation.swift); [`SecureChannel.seal/open`](https://github.com/Mukesh-devs/squick-share/blob/main/Packages/QuickShareCore/Sources/QuickShareCore/Crypto/SecureChannel.swift); [`InboundSession.run` and `handleSharing`](https://github.com/Mukesh-devs/squick-share/blob/main/Packages/QuickShareCore/Sources/QuickShareCore/Transfer/InboundSession.swift); [`OutboundSession.run`](https://github.com/Mukesh-devs/squick-share/blob/main/Packages/QuickShareCore/Sources/QuickShareCore/Transfer/OutboundSession.swift), which derives optional QR handshake signature data and supplies it to its PKE builder.
* Chromium: [`PairedKeyVerificationRunner::Run()`](https://github.com/chromium/chromium/blob/main/chrome/browser/nearby_sharing/paired_key_verification_runner.cc) and its [header](https://github.com/chromium/chromium/blob/main/chrome/browser/nearby_sharing/paired_key_verification_runner.h), including the random no-certificate fallback and reciprocal PKE/result expectations.

The read-only authenticated inspector, paired-key probe, and experimental no-credential paired-key response are implemented. The response mode sends a random 72-byte `signed_data` / 6-byte `secret_id_hash` placeholder PKE plus `UNABLE`; the bytes are not a signature, certificate, identity, or actual secret-ID hash. New unit tests are simulated schema-derived fixtures; the Android result above is a user-reported runtime observation and is not a test fixture. Android still fails after the observed PKE offer, and no successful UI connection or file transfer has been demonstrated.
